# 定期セキュリティスキャン（Snyk MCP）

## 概要
このプレイブックは、Snyk MCP連携を使用して包括的なSnykセキュリティスキャンを実行し、脆弱性を重大度別に分析し、最も重大な上位5件の脆弱性に対する修正PRを作成します。常時稼働型セキュリティガーディアンとして、スケジュール実行するよう設計されています。

**重要：すべての出力（脆弱性レポート、PRタイトル、PR説明文、コミットメッセージ、セッション内メッセージ）は日本語で記述してください。**

## ユーザーからの入力事項
- スキャン対象リポジトリ（プロンプトまたはスケジュール設定で指定）
- セッションでSnyk MCP連携が有効であること

<phase name="認証とセットアップ" id="1">
## フェーズ1：認証とセットアップ

1. `snyk_auth`を実行してSnyk MCP連携で認証する
2. 認証が成功したことを確認し、認証済みアカウントを記録する
3. リポジトリのルートフォルダに対して`snyk_trust`を実行し、スキャンを許可する
4. フォルダが信頼済みであることを確認する
5. ビルドファイル（pom.xml、package.json、build.gradle、requirements.txtなど）を調べてプロジェクトの種類を特定する

<verification>
- Snyk MCP認証が正常に完了した
- リポジトリフォルダがスキャン対象として信頼された
- プロジェクトの種類とビルドシステムが特定された
</verification>
</phase>

<phase name="包括的セキュリティスキャン" id="2">
## フェーズ2：包括的セキュリティスキャン

包括的なカバレッジのために、該当するすべてのSnykスキャンタイプを実行する：

1. **SCAスキャン（ソフトウェア構成分析）**：リポジトリパス（絶対パス必須）と`unmanaged: true`で`snyk_sca_scan`を実行する。依存関係の既知の脆弱性をスキャンする。
2. **SASTスキャン（静的アプリケーションセキュリティテスト）**：リポジトリに対して`snyk_code_scan`を実行し、コードレベルの脆弱性を検出する。
3. **IaCスキャン（Infrastructure as Code）**：Dockerfile、Terraformファイル、Kubernetesマニフェスト、その他のIaCファイルが存在する場合、`snyk_iac_scan`を実行する。
4. **コンテナスキャン**：コンテナイメージが利用可能な場合、`snyk_container_scan`を実行する。
5. **SBOMスキャン**：SBOMファイルが存在する場合、`snyk_sbom_scan`を実行する。

各スキャンで以下を記録する：
- 検出された脆弱性の総数
- 重大度別の内訳（Critical、High、Medium、Low）
- 影響を受けるパッケージ名とバージョン
- 利用可能な場合はCVE識別子

<verification>
- SCAスキャンが完了し、結果が記録された
- SASTコードスキャンが完了し、結果が記録された
- IaCスキャンが完了し（該当する場合）、結果が記録された
- すべてのスキャン結果が重大度別の内訳とともに文書化された
</verification>
</phase>

<phase name="分析とレポート" id="3">
## フェーズ3：分析とレポート

1. すべてのスキャンタイプにわたる統合脆弱性レポートを作成する
2. 調査結果を3つのセクションに整理する：
   - **重大な調査結果**：すべてのCriticalおよびHigh重大度の脆弱性
   - **インフラストラクチャの調査結果**：IaCの問題、Dockerfileの問題、CI/CDの設定ミス
   - **Snyk MCP連携評価**：スキャンカバレッジの概要とツールのパフォーマンス
3. 各Critical/High調査結果について以下を文書化する：
   - 脆弱性のタイトルとCVE ID
   - 影響を受けるパッケージと現在のバージョン
   - 修正バージョン（利用可能な場合）
   - 重大度レベルとCVSSスコア
   - リスクの簡潔な説明
4. 重大度（Criticalを最優先、次にHigh）およびCVSSスコアで脆弱性をランク付けした優先順位付きの修復計画を作成する
5. セッション内でユーザーに完全なレポートを提示する

**重要：レポートはすべて日本語で記述すること。**

<verification>
- すべてのスキャンタイプにわたる統合脆弱性レポートが作成された
- 調査結果がCVE詳細とともに重大度別に整理された
- 優先順位付きのアクションを含む修復計画が作成された
- セッションインターフェースでユーザーにレポートが提示された
</verification>
</phase>

<phase name="自動修復" id="4">
## フェーズ4：自動修復

**重要：上位5件の最も重大な脆弱性に対してのみ修正PRを作成すること。** 重大度（Criticalを最優先、次にHigh）およびCVSSスコアでランク付けする。すべての脆弱性を修正しようとしないこと — 上位5件のみ。

既知の修正がある上位5件の各脆弱性について：

1. 修正用の専用ブランチを作成する（脆弱性ごとに1つのブランチ）
2. 修正を適用する：
   - 依存関係の脆弱性の場合：マニフェストファイル（pom.xml、package.json、build.gradleなど）のバージョンを更新する
   - コードの脆弱性の場合：推奨されるコード修正を適用する
   - IaCの問題の場合：設定ファイルを更新する
3. CVE IDを含む説明的なメッセージでコミットする
4. 以下の内容でPRを作成する：
   - タイトル：`fix: [パッケージ名] [旧バージョン]から[新バージョン]へアップグレード - [CVE-ID]を解決`
   - 説明文に含める内容：脆弱性の詳細、重大度、CVEリンク、変更内容、Snykスキャンの参照
5. **1つの脆弱性につき1つのPR — 複数の脆弱性を1つのPRにまとめないこと**
6. **各PR間でmaster/mainブランチのクリーンな状態にリセットすること** — 新しいブランチをチェックアウトする前に変更をstashまたは破棄する

**重要：PRの説明文とコミットメッセージは日本語で記述すること。**

重要：PRは常にフォークしたリポジトリ（例：`COG-GTM/<REPO_NAME>`）にプッシュし、ソース/アップストリームリポジトリには絶対にプッシュしないこと。

<verification>
- 正確に5つ（既知の修正が5つ未満の場合はそれ以下）のPRが作成された
- 各PRはCVSSスコアで最も重大な脆弱性を対象としている
- 各PRにCVE参照を含む明確なタイトルがある
- 各PRの説明文に脆弱性の詳細と修復の説明が含まれている
- すべてのPRが正しいフォーク先リポジトリを対象としている
- 複数の脆弱性を1つのPRにまとめていない
- PRタイトル、説明文、コミットメッセージが日本語で記述されている
</verification>
</phase>

## 仕様
- すべてのスキャンパスは絶対パスであること
- すべてのSCAスキャンで`unmanaged: true`を使用すること
- 1回のスキャン実行あたり最大5つの修正PR — 重大度とCVSSスコアで優先順位付け
- 脆弱性ごとに1つのPR — 修正をまとめないこと
- PRはフォーク先リポジトリ（COG-GTM/<REPO_NAME>）を対象とし、アップストリームには送らないこと
- スキャンレポートはファイルシステムへの保存だけでなく、セッションインターフェースで直接提示すること
- すべての出力は日本語で記述すること

## アドバイスとポイント
- SCAスキャンは通常最も多くの脆弱性を検出するため、最初に実行すること
- `snyk_trust`がハングする場合、信頼確認サーバーの`/trust`エンドポイントにHTTP POSTが必要な場合がある
- Java/Mavenプロジェクトの場合、正確な依存関係解決のためにMavenが利用可能であることを確認すること
- 既知の修正がある上位5つの脆弱性に修復を集中すること — パッチが利用できないものはスキップする
- 依存関係をアップグレードする際は、メジャーバージョン間の破壊的変更を確認すること
- 各修正ブランチを作成する前に、クリーンなgit作業ディレクトリ（git checkout master && git checkout -- .）を確保すること

## 禁止事項
- 認証をスキップしないこと — `snyk_auth`を最初に実行する必要がある
- 1回の実行で5つを超える修正PRを作成しないこと
- 複数の脆弱性を1つのPRにまとめないこと
- アップストリーム/ソースリポジトリにPRをプッシュしないこと — 常にフォーク先リポジトリを使用する
- 文書化された正当な理由なく脆弱性を抑制または無視しないこと
- 依存関係のアップグレード後にテストを通すためにテストファイルを変更しないこと
- 英語で出力しないこと — すべての出力は日本語であること
